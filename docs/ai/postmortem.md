# Project Postmortem

Observations grounded in commit history, spec files, and the running
codebase. Subjective reflections are explicitly marked.

---

## What worked

- **Two-spec split (architecture / implementation).** Forcing the
  architecture spec to be documentation-only (Architecture Req 2.3) kept
  the design clean and let the implementation spec inherit all 27
  requirements verbatim. Both `.config.kiro` files record different
  Kiro workflow types, and both spec sets are committed.
- **Phase boundaries map cleanly to commits.** Phase 1 = `eca4b19`,
  Phase 2 = `44ac6a5` + `7bd3ac8`, Phase 3 = `4451ac7`, cleanup =
  `5141b1c`. Each phase commit corresponds exactly to its tasks.md scope.
- **Property-based testing surfaced rules early.** Six `*_property_test.go`
  files live alongside the components they verify (argv, capture,
  classifier, reaper, workspace, pool). The
  `pgregory.net/rapid`-driven generators exercise the universally
  quantified architecture properties (17, 18, 19, 36, 37, 38, 39) far
  more thoroughly than table tests would have. Subjective: the discipline
  of writing the property statement first kept the API of each pure
  function honest.
- **Observer-interface pattern preserved the dependency graph.** Four
  Observer interfaces (`SandboxObserver`, `WorkspaceObserver`,
  `ReaperObserver`, `worker.Observer`) let `internal/runner` and
  `internal/worker` emit metrics and logs without importing
  `internal/metrics` or `internal/log`. `tests/structure_test.go`
  enforces the no-cycle invariant at every `make test` run.
- **`make test` and `make lint` ran reliably.** Tasks 28, 29, 31 closed
  cleanly. The cleanup commit `5141b1c` is pure deletion (0 insertions,
  31 deletions), evidence that the codebase had reached a stable state.

## What didn't work

- **`make integration` is unreachable on the shipped infrastructure.**
  The `tools` service in `docker-compose.yml` is unprivileged; nsjail's
  `clone(CLONE_NEW…)` returns `Operation not permitted`; the runtime
  classifier reports `RUNTIME_ERROR` (correctly per spec); integration
  tests fail. The fix lives in `docker-compose.yml`, which Task 32
  forbids editing. See `docs/ai/issues.md` for the full reproduction
  and reasoning. Task 30 was reclassified BLOCKED OUTSIDE CODEBASE.
- **`docs/architecture.md` was missed until final audit.** Architecture
  Req 1.1 mandates the file. It was never produced during Phase 1, 2,
  or 3 because no implementation task in
  `.kiro/specs/goboxd-implementation/tasks.md` claimed ownership of it.
  Implicitly, the spec's own design.md line 9 expected it to be
  generated by "mechanical expansion" of the spec — and that mechanical
  step was never scheduled.
- **`tasks.md` checkboxes never updated.** Both spec tasks files still
  show every task as `- [ ]` despite tasks 1–31 having been delivered.
  Progress tracking ended up living in commit messages, which worked
  but was not the design intent.
- **Audit findings were ephemeral.** Phase 2 Wave E audit, Phase 3
  audit, and the Task 30 investigation were conducted in development
  conversations and never committed as in-repo artefacts. The
  documentation tree this postmortem belongs to is the first attempt
  to put that evidence under version control.
- **Phase 3 left two metrics counters without dedicated nil-safety
  tests** (`IncUnsafeFilename`, `IncUnknownPlaceholder`). The
  implementations are nil-guarded; only the matching `*NilSafe` tests
  are missing. Pattern drift, not a runtime defect.

## Surprises

- **arm64 base images do not ship `/lib64`.** The default
  `SANDBOX_RO_MOUNTS` value (recorded in Architecture design §15) was
  amd64-centric. arm64 Linux deliberately omits `/lib64`. The Task 30
  arm64 fix (`db4b14a`, 16-line test-helper override) is small but the
  symptom was opaque: integration tests timed out waiting for the HTTP
  listener because the prereq check rejected `/lib64` before the
  listener ever opened.
- **Same image, same nsjail, same kernel — but `clone()` succeeds with
  `--privileged` and fails without it.** Once isolated, this was
  obvious; until isolated, it looked like an arch-specific Docker
  Desktop / LinuxKit issue. The decisive evidence was running the
  identical command via `docker run --privileged` and watching it
  succeed end-to-end on the same host.
- **The architecture spec's `design.md` is structurally a planning
  document, not an architecture document.** Twelve top-level section
  headers literally read "(plan for `docs/architecture.md` §N)". A
  verbatim copy was not possible; the deliverable required a structural
  transform. Subjective: this only became clear when reading the spec
  with the requirements file open in parallel — the requirements
  describe a different document than the design produces.

## What we'd do differently next time

- **Schedule documentation deliverables as tasks in `tasks.md`.**
  Architecture Req 1.1 has been a deliverable from day one; no
  implementation task ever pointed at it. A single explicit task
  ("Task X: Produce `docs/architecture.md` from design.md per
  Req 1.1") would have closed the gap.
- **Maintain `tasks.md` as work progresses, or stop treating it as a
  tracker.** Either every commit that completes a task ticks the box,
  or the tasks.md is frozen as the original plan and progress is
  tracked elsewhere (commit history, a separate `progress.md`). The
  current state — tasks.md frozen but informally treated as truth —
  is misleading.
- **Verify `docker-compose.yml` privileges before committing to a
  Task 32-style infrastructure freeze.** The frozen-infrastructure
  constraint is sound in intent but should be paired with a check
  that the frozen infrastructure can actually run the test suite
  it gates on.
- **Commit audit and investigation reports.** Phase 2 Wave E audit,
  Phase 3 audit, and the Task 30 investigation all produced useful
  evidence and reasoning that lived only in conversation. A simple
  `docs/ai/audits/` directory with timestamped markdown would have
  preserved them.
- **Add a CI gate for spec-mandated artefacts.** A 10-line shell check
  that fails if any path enumerated as a deliverable in
  `requirements.md` is missing would have flagged
  `docs/architecture.md` on the first push.
- **Make `SANDBOX_RO_MOUNTS` defaults platform-aware, or document the
  arm64 expectation.** Subjective: the right place for this is the
  architecture spec's Configuration Reference §15, not a test helper.
